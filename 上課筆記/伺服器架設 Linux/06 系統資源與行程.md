## 一、觀念篇：程式、行程與資源

### 程式 vs 行程

- **程式（program）**：放在硬碟上的檔案，靜態的。
- **行程（process）**：程式被執行後，在記憶體中「活著」的實體，有自己的編號 **PID**，也有「爸爸」**PPID**（父行程）。

類比：食譜是程式，照食譜正在煮的那一鍋就是行程。同一份食譜可以同時有很多鍋。

### 一個應用系統需要什麼？

不要只想到「程式本身」。以一個網站為例，還包括**資料庫、網路、儲存**。就算是虛擬機，VM 的規格也等於基礎建設資源。管理員要知道：

- 系統需要多少資源才跑得順。
- 資源太少 → 系統慢、當機；資源太多 → 浪費錢（企業對成本很敏感）。
- 所以平常就要觀察使用量，才能**準確估算**，避免低估或高估。

### 主要硬體資源

| 資源 | 重點 |
|---|---|
| **CPU** | 核心數（多核心可同時跑多個行程）、時脈與架構（決定速度） |
| **記憶體（RAM）** | 容量要夠，才不用依賴很慢的虛擬記憶體；**ECC RAM** 能自動修正位元錯誤，資料庫、伺服器常用 |
| **儲存** | HDD 容量大但慢、SSD 快但貴；I/O 速度影響檔案操作與開機時間 |
| **網路介面** | 1G／10G 等頻寬，依需求選擇 |
| **輸入輸出設備** | 依使用者互動需求 |

### 行程運作時使用的資源

| 項目 | 說明 |
|---|---|
| **CPU 時間** | 作業系統依優先權和公平原則，把 CPU 時間切片分給行程；多核心時還要把行程平均分配到各核心 |
| **記憶體** | 每個行程要有空間放指令與資料；實體記憶體不足時，核心會借用硬碟當**虛擬記憶體（swap）**，能續跑但**會變慢** |
| **I/O** | **同步 I/O**：行程要等做完才繼續；**非同步 I/O**：等的時候可以做別的事。核心用緩衝區、排隊來最佳化 |

### 核心（kernel）在背後做的事

行程調度、記憶體管理（分配/回收、虛擬記憶體）、I/O 調度與驅動、資源限制與監控（如 cgroup）、權限管理與行程隔離（namespace，這也是之後 Container 的基礎）。這個領域可以獨立成一門課，這裡只要有大方向的概念。

## 二、五大觀察指標

> 排查系統問題的第一步：**先判斷是哪一類資源出問題，再找是哪個行程造成的。**

| 指標 | 常用工具 |
|---|---|
| CPU 使用率 | `top` |
| 系統負載 | `uptime`、`top` |
| 記憶體 | `free -h` |
| 磁碟空間／I/O | `df -h`、`df -i`、`iostat` |
| 網路流量 | `ethtool`、`sar -n DEV`、`ip -s link` |

### 1. CPU 使用率：`top`

```bash
top
```

畫面解讀（範例）：

```text
top - 22:48:13 up 120 days, 7:52, 1 user, load average: 0.00, 0.01, 0.05
Tasks: 140 total,   1 running, 139 sleeping,   0 stopped,   0 zombie
%Cpu(s):  0.0 us,  0.0 sy,  0.0 ni,100.0 id,  0.0 wa,  0.0 hi,  0.0 si,  0.0 st
KiB Mem : 32668368 total,  9858468 free,   316248 used, 22493652 buff/cache
KiB Swap: 16777208 total, 16776184 free,     1024 used. 31743824 avail Mem

  PID USER   PR  NI    VIRT    RES    SHR S  %CPU %MEM     TIME+ COMMAND
 3206 root   20   0  162012   2288   1588 R   0.3  0.0   0:00.13 top
```

| 區塊 | 說明 |
|---|---|
| 第 1 行 | 現在時間、開機多久、登入人數、**load average**（1／5／15 分鐘） |
| `Tasks` | 行程總數與狀態統計（running 執行中、sleeping 睡眠、stopped 停止、**zombie 殭屍**） |
| `%Cpu(s)` | CPU 花在哪：`us` 使用者程式、`sy` 核心、`ni` 低優先權、**`id` 閒置**、**`wa` 等 I/O**、`hi/si` 中斷、`st` 被虛擬化偷走的 |
| `Mem`／`Swap` | 記憶體與交換區 |
| 行程列表 | 每行一個行程（預設按 CPU 排序） |

**`top` 裡的快速鍵**

| 按鍵 | 功能 |
|---|---|
| `q` | 離開 |
| `u` | 只顯示某使用者的行程 |
| `k` | 殺掉行程（輸入 PID，再選訊號） |
| `r` | 調整優先權（renice） |
| `P` | 依 CPU 排序 |
| `M` | 依記憶體排序 |
| `1` | 展開每個 CPU 核心的使用率 |
| `h` | 說明 |

CPU 欄位小撇步：`wa`（I/O wait）很高，代表 CPU 在等硬碟，而不是 CPU 太忙，問題在儲存。

### 2. 系統負載（Load Average）

`uptime` 輸出：

```text
23:18:12 up 120 days, 8:22, 1 user, load average: 0.00, 0.01, 0.05
```

- 三個數字依序代表 **過去 1 分鐘、5 分鐘、15 分鐘** 的平均「排隊等 CPU（或等 I/O）的行程數」。
- 1 分鐘看**短期變化**，5 分鐘看**中期**，15 分鐘看**長期趨勢**。
- **它不是百分比**，要跟 **CPU 核心數**一起看：
  - 單核心，load 1.0 = 滿載。
  - 4 核心，load 1.0 = 25%。

**怎麼知道有幾個核心？**

```bash
grep processor /proc/cpuinfo      # 有幾行就是幾核，編號從 0 開始
nproc                             # 更簡單，直接印出數量
lscpu                             # 完整資訊
```

**換算成百分比**

```text
(load average ÷ 核心數) × 100 = 負載百分比
```

例：4 核心、1 分鐘 load = 1.6 → (1.6 ÷ 4) × 100 = **40%**。這只是粗估，但很直觀。

**load 高但 CPU 使用率低？** 通常是 **I/O 在拖後腿**（磁碟、NFS 網路磁碟慢），看 `top` 的 `wa` 與 `iostat`。

造成高負載的常見原因：核心數不夠、I/O 太忙、記憶體不足導致 swap、網路或磁碟空間問題、異常行程。

### 3. 記憶體：`free -h`

```bash
free -h
```

```text
              total        used        free      shared  buff/cache   available
Mem:          3.6Gi       308Mi       867Mi        73Mi       2.5Gi       3.0Gi
Swap:         2.0Gi          0B       2.0Gi
```

| 欄位 | 白話說明 |
|---|---|
| `total` | 總實體記憶體（會比購買規格少一點，因為核心與硬體保留；`dmesg \| grep -i memory` 可看） |
| `used` | 行程**真正在用**的 |
| `free` | **完全沒人用**的 |
| `buff/cache` | 拿來當緩衝與快取的（可以被快速回收） |
| `available` | **新程式還能用多少而不必 swap**（最重要！） |
| Swap `used` | 若很高，代表實體記憶體不夠 |

> [!tip] 為什麼 free 很少但系統很健康？
> Linux 會**盡量把閒置記憶體拿來當快取**（因為閒著也是浪費），所以 `buff/cache` 常常很大、`free` 很小。需要時快取馬上能釋放。**看 `available` 才準**。
> 上例 free 只有 867Mi，但 available 有 3.0Gi，完全沒問題；Swap used = 0 也是好現象。

**Buffer 與 Cache 簡單概念流程**

1. 讀硬碟資料 → 先載入記憶體的 cache。
2. CPU 需要時先看 CPU 內部快取，找不到再去記憶體。
3. 資料被修改後先標記，等適當時機再寫回硬碟。

這樣能彌補 CPU 與硬碟之間的速度差。

資料來源是 `/proc/meminfo`，也可用 `vmstat 1 5` 觀察變化。

### 4. 磁碟空間與 I/O

**(1) 容量：`df -h`**

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/sdb2        50G   46G  4.2G  92% /
/dev/sda        894G  886G  8.7G 100% /VM
/dev/sdb1      1014M  180M  835M  18% /boot
tmpfs            16G     0   16G   0% /dev/shm
```

只要看 `/dev/` 開頭的（實體裝置），`tmpfs` 之類是記憶體虛擬的。解讀：

- `/` 用了 92%，雖然還有 4.2G，但要查是什麼佔了空間（可能是大檔案或沒清的垃圾）。
- `/VM` 已經 **100%**，獨立分割又滿了，要立即處理，否則應用程式可能異常。
- `/boot` 18%，健康。

找出誰佔空間：

```bash
du -sh /var/* 2>/dev/null | sort -h | tail
```

**(2) inode 數量：`df -i`**

每個檔案或目錄都要佔一個 **inode**（索引節點），它記載：類型、權限、擁有者與群組、時間戳記、大小、資料位置、連結數。檔案系統建立時，inode 總數就固定了。

```bash
df -i | grep -E '^/dev|Filesystem'
```

```text
Filesystem       Inodes IUsed    IFree IUse% Mounted on
/dev/sdb2      26214400 38019 26176381    1% /
```

> [!warning] 容量還有，卻寫不進檔案？
> 如果程式一直產生**大量小檔案**又沒清理（例如 session 檔、郵件佇列），`IUse%` 會先到 100%。這時 `df -h` 看起來還有空間，卻會出現 `No space left on device`。**一律連 `df -i` 一起檢查**。

**(3) 磁碟 I/O：`iostat`（需要安裝 `sysstat`）**

```bash
sudo dnf install -y sysstat
iostat -dx 1 2 | awk 'BEGIN {OFS="\t"}; NR > 6 {print $1, $4, $5, $6, $7, $14}'
```

取樣 2 次、每次間隔 1 秒，只挑 1、4、5、6、7、14 欄位（欄位位置會因 sysstat 版本略有不同，需對照實際輸出）：

| 欄位 | 意義 |
|---|---|
| `r/s`、`w/s` | 每秒讀、寫次數 |
| `rkB/s`、`wkB/s` | 每秒讀、寫 KB |
| `%util` | 磁碟忙碌程度，接近 100% 代表磁碟已經飽和 |

如果在**非預期的時間**突然 `%util` 飆高，要查是哪個程式；如果**長期**很高，代表磁碟速度已不夠用，需要放寬 VM 的 I/O 限制或升級儲存設備。

### 5. 網路流量

企業主的角度：被使用的系統應該有流量，沒人用卻有大量流量或高使用卻零流量都**不正常**。

**(1) 實體連線狀況：`ethtool`**

先找介面名稱：

```bash
ip link show | grep '^[0-9]' | awk '{print $1, $2}'
# 1: lo:    2: eno1:    3: wlp1s0:   4: br0:   5: virbr0: ...
```

`lo` 是本機回送、`virbr0` 等是虛擬橋接，`eno1` 是實體網卡。

```bash
ethtool eno1
```

重點看：

- `Speed: 1000Mb/s`（目前速度）、`Duplex: Full`（全雙工）
- `Supported link modes`（網卡支援的速度）
- `Link detected: yes`（有接上線）

**(2) 流量：`sar -n DEV`（也是 sysstat 套件）**

```bash
sar -n DEV 1 1 | grep -E 'IFACE|eno1'
```

| 欄位 | 意義 |
|---|---|
| `rxpck/s`、`txpck/s` | 每秒收／送封包數 |
| `rxkB/s`、`txkB/s` | 每秒收／送 KB |

定期觀察，才能看出「非預期的流量變化」。

## 三、系統行程管理

Linux 是**多人多工**作業系統。管理員雖然不知道程式內部細節，但可以觀察：**有沒有從沒看過的行程**（資安）、**資源用量是否異常**。

### 看行程：`top` 的行程欄位

| 欄位 | 說明 |
|---|---|
| **PID** | 行程編號（唯一） |
| **USER** | 誰執行的（追責任、查資安） |
| **PR／NI** | 優先權／nice 值（越小越優先，-20 到 19） |
| **VIRT／RES／SHR** | 虛擬／實際／共用記憶體 |
| **S** | 狀態（見下表） |
| **%CPU／%MEM** | CPU、記憶體使用百分比 |
| **TIME+** | 累積用掉的 CPU 時間 |
| **COMMAND** | 怎麼啟動的，可疑程式從這裡看 |

### `ps`：一次列出所有行程快照

`top` 是互動、持續更新；`ps` 是「拍一張照」，適合搭配管線處理。

```bash
ps aux             # BSD 風格：所有使用者、含沒有終端機的行程、詳細欄位
ps -ef             # System V 風格：全部行程、完整格式
ps auxf            # 加 f：樹狀顯示父子關係
ps -eo pid,user,pcpu,pmem,stat,cmd --sort=-pcpu | head   # 自訂欄位 + 依 CPU 排序
```

`ps aux` 欄位：

| 欄位 | 說明 |
|---|---|
| USER／PID | 擁有者／行程編號 |
| %CPU／%MEM | CPU／記憶體使用率 |
| **VSZ** | 虛擬記憶體大小（KB） |
| **RSS** | 實際佔用的實體記憶體（KB） |
| TTY | 關聯的終端（`?` 代表沒有，常見於背景服務） |
| **STAT** | 狀態 |
| START／TIME | 啟動時間／累積 CPU 時間 |
| COMMAND | 啟動指令 |

**STAT 狀態碼**

| 代碼 | 意義 |
|---|---|
| `R` | 執行中／可執行 |
| `S` | 睡眠（可被喚醒，大多數行程是這個） |
| `D` | 不可中斷睡眠（通常在等 I/O，卡住時殺不掉） |
| `T` | 被停止（如按了 Ctrl+Z） |
| `Z` | **殭屍行程**（已結束但父行程沒回收） |
| 附加 `s` | session leader；`+` 在前景；`<` 高優先權；`N` 低優先權；`l` 多執行緒 |

### 看父子關係（樹狀）

```text
root   15465 ... Ss  nginx: master process /usr/sbin/nginx
apache 15466 ... S    \_ nginx: worker process
apache 15467 ... S    \_ nginx: worker process
```

`nginx: master` 是 root 啟動的**父行程**，底下兩個縮排的 `worker` 是它建立的**子行程**（以較低權限用戶運行）。排查服務時這個關係很有用：殺了 worker，master 會再生；要停服務，應該用 `systemctl stop`（見 [[11 systemd 與日誌]]）。

其他好用的：`pstree -p`、`pgrep nginx`（直接找 PID）、`pidof`、`ps -p PID -o pid,ppid,user,stat,pcpu,pmem,cmd`。

## 四、結束行程：`kill`

### 流程

1. **找 PID**（`ps`、`top`、`pgrep`）。
2. **送出訊號**（`kill`）。

重點：`kill` 其實不是「殺」，而是**傳送訊號**，行程收到後自己決定怎麼處理（有些訊號無法被攔截）。

```bash
kill -l       # 列出全部訊號（共 60 多個）
```

### 三個最重要的訊號

| 訊號 | 編號 | 作用 | 使用時機 |
|---|---|---|---|
| **SIGTERM** | 15 | 禮貌地請求結束，行程可以收尾（存檔、關連線、釋放資源） | **預設，優先用** |
| **SIGKILL** | 9 | 立即強制消滅，**不給任何清理機會**，無法被攔截 | SIGTERM 無效時的**最後手段** |
| **SIGINT** | 2 | 等同 `Ctrl+C` | 結束前景程式 |

其他你會遇到的：`SIGHUP`(1) 常用來要服務**重新讀取設定**；`SIGSTOP`(19)／`SIGCONT`(18) 暫停／繼續；`SIGTSTP`(20) 等同 `Ctrl+Z`。

### 練習：用 sleep 體驗

終端機 1：

```bash
sleep 600       # 睡 10 分鐘
```

終端機 2：

```bash
ps aux | grep sleep
# student   25065  0.0  0.0 107952   360 pts/0  S+  13:12  0:00 sleep 600
kill 25065      # 預設送 SIGTERM(15)
```

回到終端機 1，會看到 `Terminated`，sleep 被終止。

> [!tip] 更簡單的方式
> `pgrep -a sleep` 直接找；`pkill sleep` 依名稱結束（小心會殺掉所有同名行程）；`killall` 同理。**大範圍的指令執行前先 `pgrep -a` 核對**。

### 安全結束行程的標準流程

```bash
ps -p <PID> -o pid,ppid,user,stat,pcpu,pmem,cmd   # 1. 確認這就是我要殺的
kill -TERM <PID>                                   # 2. 先請它好好結束
sleep 2
ps -p <PID>                                        # 3. 還在嗎？
kill -KILL <PID>                                   # 4. 真的不走才強制
```

> [!warning] 別一開始就 `kill -9`
> SIGKILL 讓行程沒機會收尾 → 可能留下**損毀的檔案、鎖定檔、資料庫不一致**。也別憑記憶用昨天的 PID，**PID 每次都會變**，每次先重查並確認 `cmd`。

## 五、LAB：找出忙碌行程（NTUB 練習）

用 batch 模式讓 `top` 的輸出能接管線處理：

```bash
top -b -n 1 | grep -A 3 'PID' | tail -n 3
top -b -n 1 | head -n 10 | tail -n 3
```

- `-b`：batch（非互動）模式
- `-n 1`：只更新 1 次就結束
- `grep -A 3 'PID'`：找到標題列，**並多印後面 3 行**（After）
- `tail -n 3`：只取最後 3 行 → 也就是最忙碌的前 3 個行程
- 第二種寫法：取前 10 行再取最後 3 行（因為 `top` 前 7 行是統計摘要）

更直覺的替代方案：

```bash
ps -eo pid,user,pcpu,pmem,comm --sort=-pcpu | head -n 4
```

## 六、LAB：中斷行程（NTUB 練習）

在測試 VM 開兩個終端機。

**Terminal-1**：寫一個會一直吃 CPU 的腳本

```bash
vi run.sh
```

```bash
#!/bin/bash
c=0
while true; do
    ((c++))
    echo $c
done
```

```bash
chmod +x run.sh
./run.sh            # 數字會一直狂噴
```

**Terminal-2**：用 `top` 殺

```text
top
  PID USER    ... %CPU COMMAND
10533 student ... 64.7 run.sh     ← 它在 CPU 排行榜第一名
```

在 top 裡按 `k` → 輸入 PID（如 `10533`）→ 輸入訊號 `15` → Enter，Terminal-1 的腳本會停止。

**換成 ps + kill**：再執行一次 `./run.sh`，在 Terminal-2：

```bash
ps auxf | grep '[r]un.sh'      # [r] 技巧：避免把 grep 自己列進來
kill <PID>                     # 原文寫 kill {PID}，要把花括號換成真實數字
```

觀察 Terminal-1 是否被終止。

> [!warning] 只在測試環境做
> 這個腳本會把 CPU 吃到飽，不要在正式主機跑。

## 七、排查流程小抄

```bash
uptime                                   # ① 負載（要除以核心數）
free -h                                  # ② 記憶體（看 available）
df -hT ; df -i                           # ③ 空間與 inode
ps -eo pid,user,pcpu,pmem,stat,cmd --sort=-pcpu | head    # ④ 誰最忙
ps -p <PID> -o pid,ppid,user,stat,pcpu,pmem,cmd           # ⑤ 確認身分
kill -TERM <PID>                                          # ⑥ 先禮後兵
```

先判斷哪類資源異常，再找對應行程。**看到 CPU 高不要立刻殺**——先確認是什麼指令、誰啟動的、有沒有父子關係。
